# 铁路购票系统 —— 技术方案 v2（评审修订版）

> 相对 v1 的核心修订（v1 即用户提供的完整技术方案，v2 在其上修正内部矛盾，**加粗为改动/新增点**）：
>
> 1. **新增《模型策略与路由》章节**，落实「开发期基座=V4 Pro、上线后 Agent/多模态核心=V4 Flash」两阶段策略，模型名全部走配置，不写死。
> 2. **修正生成模型缺位**：Qwen3-Embedding-0.5B 是纯 embedding 模型，无法"生成答案/判断规则"。v1 中"送入 vLLM 生成答案"的表述错误，v2 改为：答案生成、规则的自然语言判定统一由**模型路由层（V4 Pro/V4 Flash）**完成。
> 3. **权限硬化**：职级/部门等硬约束从"LLM 判定"下沉到 **Java 确定性规则校验 + Milvus 标量过滤**，LLM 只做解释，不做放行。
> 4. **执行通道收敛**：Agent→Java 只走一条 REST 通道；MCP 仅作为工具注册/元数据（预留外部 Agent 接入），避免双契约漂移。
> 5. **WSL2 内存账重算**：v1 按 Linux 单机 16GB 估算，实际是 Windows 宿主机 + WSL2，需 `.wslconfig` 并统一内存池。
> 6. Spring AI 生态无原生 `@McpTool`，v2 标注真实落地方式（`@Tool` + `McpServer`/ToolCallback），不改变设计意图。

---

## 1. 项目定位与核心目标

一句话定位：一个 AI 驱动的央国企内部资源（班车座位、会议室、福利等）智能预约与高并发抢购平台。

核心目标：员工通过**自然语言对话**即可完成资源预约，后端由**高并发交易引擎**和**智能 RAG 知识库**共同支撑。

## 2. 模型策略与路由（NEW，全案前提）

### 2.1 两阶段模型策略（用户拍板）

| 阶段 | 通用生成/基座（RAG 答案合成、兜底对话） | Agent 核心（意图识别→决策→工具调用） | 多模态理解（文档图片） | 向量化 Embedding |
|---|---|---|---|---|
| **开发期（现在）** | **deepseekv4pro** | **deepseekv4pro** | **deepseekv4pro**（若其支持图片则统一走它） | Qwen3-Embedding-0.5B（本地 vLLM） |
| **上线后（开发成功）** | **deepseekv4pro**（默认基座不变） | **deepseekv4flash** | **deepseekv4flash** | 同上（不变） |

> 决策说明：Agent 与多模态上线后是高频调用路径，切 Flash 以降本降延迟；通用生成保底仍走 V4 Pro 保证质量。开发期统一用 V4 Pro，避免两套行为差异干扰联调。

### 2.2 模型路由实现要求（落地约束）

1. **Python 侧统一 `llm_client`**：只暴露一个 `chat(model_alias, messages, tools, stream)` 接口，内部分发到 V4 Pro / V4 Flash 的 API。
2. **任务→模型映射全部配置化**，业务代码禁止出现写死的模型名：
   - 配置文件按环境分档（`dev` / `prod`），键如：`MODEL_AGENT`、`MODEL_MULTIMODAL`、`MODEL_GEN`。
   - 切换只需改环境变量/配置，**不需要改代码**。
3. **可观测**：SSE 推送与后端日志中显式携带 `model` 字段，方便确认「dev 路由到 v4pro、上线后路由到 v4flash」。
4. **tool-call 契约与模型解耦**：工具/函数的 schema 只描述 Java 侧能力，不随模型名变化；若某模型不支持原生 function-calling，则由 llm_client 用"输出 JSON action 再本地解析"的兜底协议兼容（开发期默认按支持 function-calling 对齐）。

### 2.3 生成/推理职责归属（修正 v1 错误）

- vLLM 内运行的 **Qwen3-Embedding-0.5B 只负责"向量化"，不具备生成能力**。
- 所有需要"产出文本/做判断"的动作——意图识别、RAG 答案合成、规则的自然语言解释——一律由 **2.1 的模型路由层**承担，**绝不委托给 embedding 服务**。

## 3. 总体架构

### 3.1 宏观架构：前端统一认证 + Java-Python 异构双后端

| 层级 | 技术选型 | 职责 |
|---|---|---|
| 前端 | Vue / React | 登录页 + 业务交互界面，所有请求携带 JWT |
| Java 后端 | Spring Boot 3（内嵌 Tomcat） | 登录认证（签发/校验 JWT）+ 高并发交易核心 + **确定性权限规则校验（NEW）** |
| Python 后端 | FastAPI + vLLM + Milvus Lite | Token 校验中间件 + **模型路由层（NEW）** + Agent 调度中枢 + RAG 检索引擎 |
| 通信 | **统一 REST（执行通道）；MCP 仅作工具注册元数据（预留）** | Agent 决策后经 REST 调用 Java；工具 schema 通过 MCP/注解维护 |
| 基础设施 | Redis（缓存 + Stream 消息队列）+ MySQL | 见 3.2 |

### 3.2 中间件层（精简部署清单）

| 组件 | 版本/模式 | 职责 | 资源预估 |
|---|---|---|---|
| Redis | 单机（Docker，WSL2 内） | 缓存（库存预热）+ 分布式锁（Redisson）+ Stream 消息队列 | ~500MB 内存 |
| MySQL | 单机（Docker，WSL2 内） | 订单、用户、资源、**权限规则表** | ~300MB 内存 |
| Milvus Lite | 嵌入式（随 Python 进程，WSL2 内） | 向量存储与检索（Small-to-Big，含部门/职级标量过滤） | ~3GB 内存 |
| vLLM | WSL2 内 | 仅加载 Qwen3-Embedding-0.5B | 6GB 显存内 + ~1.5GB 内存 |
| 模型路由 | **Python 进程内出站 API（NEW）** | 调 deepseekv4pro / deepseekv4flash | 0（外网 API） |
| 配置管理 | 环境变量 / 配置文件（dev、prod 两档） | JWT 密钥、模型映射、Redis 地址 | 0 |
| 异步削峰 | Redis Stream 替代 RabbitMQ（MAXLEN=10000） | 订单落库削峰 | 复用 Redis 内存 |

## 4. Java 后端详细设计

### 4.1 模块组成

| 模块 | 功能 | 关键技术 |
|---|---|---|
| 认证模块 | 登录接口，签发 JWT | Spring Security / JJWT |
| 购票核心 | 秒杀下单、库存扣减、订单生成 | Redis 缓存预热 + Lua 原子扣减 |
| 限流模块 | 全局限流 | Redis + Lua 令牌桶（QPS=1000） |
| 幂等模块 | 防重复下单 | Redisson 分布式锁（锁 key=request_id）+ 唯一索引(user_id, product_id) |
| **权限校验（NEW）** | 按职级/部门做确定性放行判断 | **规则表 + Token 身份 + Milvus 检索过滤的兜底** |
| 工具暴露 | 将购票/权限校验等能力注册为工具描述 | Spring AI **`@Tool`** + MCP Server 装配（非 `@McpTool` 原生注解） |
| REST 暴露 | 供 Python 调用的 HTTP 接口 | Spring MVC `@RestController` |

### 4.2 权限校验（v2 硬化设计，替换"LLM 当闸门"）

- 新增**权限规则表**（入库，Java 可查）：`(resource_type, required_position, allowed_departments, ...)`，如「总裁班车 → 职级 ∈ {高管…}」。
- **Java 校验流程**：解析 Token 拿到 user_id/name/department/position → 查资源对应规则 → 确定性放行/拒绝。该判断**不经过任何 LLM**。
- 校验不通过 → 返回明确的业务错误码（如 `PERMISSION_DENIED`），Python 层据此向用户解释原因（解释文案可由模型润色，但结论是 Java 给的）。
- Milvus 侧的部门过滤作为**检索可见性**约束（见 5.3），与 Java 规则校验互补，二者都是确定性的。

### 4.3 关键设计决策

- **统一参数 POJO**：`SeckillRequest` 同时用于 REST `@RequestBody` 与工具参数定义，保持一致。
- **双通道一致性**：v2 中 Python **只经 REST 调用 Java**；`@Tool`/MCP 仅用于登记"Java 有哪些工具可用"（供 Agent 决策 + 供外部 MCP Agent 预留）。启动时反射/装配校验所有注册工具都有对应 REST 接口，防止双契约漂移。
- **双重保障**：Python 层 Token 校验通过后，Java 仍二次校验 Token（含权限），记录审计日志（谁-何时-抢了什么）。
- `@McpTool` 非 Spring AI 原生注解，落地用 `@Tool`（Spring AI）描述工具能力 + `McpServer`（ToolCallbackProvider）暴露。

## 5. Python 后端详细设计

### 5.1 模块组成（四合一：Token 校验 + 模型路由 + Agent + RAG）

| 子模块 | 功能 | 关键技术 |
|---|---|---|
| Token 校验中间件 | 解析 JWT，提取身份（ID/姓名/职级/部门），注入上下文 | python-jose（与 Java 同密钥） |
| **模型路由层（NEW）** | 按 2.2 配置把任务分发到 deepseekv4pro / deepseekv4flash | 统一 `llm_client` + 配置路由 |
| RAG 检索引擎 | 文档解析（MD/Word/PDF）、向量化、Small-to-Big 检索 | Qwen3-Embedding-0.5B + Milvus Lite |
| 多模态理解 | 处理文档中的图片 | 经**模型路由层**调 V4 Flash（上线后） |
| Agent 调度中枢 | 意图识别、决策、规则解释、调用 Java | LangChain / 自研调度器 |
| Java 调用客户端 | REST 调用 Java 交易与权限接口 | httpx / aiohttp |
| SSE 流式响应 | 逐步推送「思考中→检索中→验证权限→执行抢票→成功」 | FastAPI StreamingResponse |

### 5.2 Agent 决策与权限的边界（修正 v1）

- **Agent 不承担放行决策**。流程为：意图识别（模型）→ 工具调用意向 → 把"抢总裁班车 + 身份=高级工程师"发给 **Java 权限接口**做确定性校验 → Java 返回 通过/拒绝 → 通过则继续调用交易接口。
- LLM 的"规则判断"仅用于**向用户解释** Java 给出的结论（如"您当前职级不可预约总裁班车"），结论源是 Java 规则表，不是模型幻觉。

### 5.3 Small-to-Big 检索策略（含可见性过滤）

存储：Milvus Lite 存子块（Small）向量，记录带 `parent_id` + **`dept_tags`/`position_tags` 标量元数据**。

检索：
1. 用户查询 → 向量检索召回 Top-K 子块，**携带标量过滤**：`dept in [用户部门]` 或公开标记，用户不可见的文档从检索层就不出现（可见性兜底）。
2. 按 `parent_id` 去重。
3. 拼接完整父块（Big）作为上下文。
4. 上下文交**模型路由层**生成答案（不是 vLLM embedding）。

### 5.4 模型生命周期（沿用 v1）

- Qwen3-Embedding-0.5B 随 Python 进程启停加载/释放；`max_model_len=2048`；加载失败则进程退出由 systemd/supervisor 重启。此策略仅针对本地 embedding，与模型路由层（外接 API）无关。

## 6. 认证与鉴权流程

### 6.1 登录认证（前端 → Java）

1. 前端调 Java `/login` → Java 校验账号密码 → 签发 JWT（含 user_id/name/department/position/role）→ 前端存储，后续请求携带 `Authorization: Bearer <token>`。

### 6.2 请求鉴权（Python 中间件）

1. 解析 Token → 校验签名/有效期 → 失败返回 401，不进入 RAG、不调用 Java。
2. 成功 → 提取身份注入上下文 → 进入 Agent。

### 6.3 Java 层二次校验

1. Java 接口再次校验 Token + **确定性权限校验（4.2）**。
2. 记录审计日志。

## 7. 核心业务流程完整闭环（v2 改写）

### 7.1 阶段一：登录
用户登录 → Java 签发 JWT → 前端存储 Token。

### 7.2 阶段二：智能预约（含 Token 传递与权限硬化）
1. 用户输入"帮我抢下周一的总裁班车座位"，Header 携带 Token。
2. Python 中间件：校验 Token → 身份"张工，技术部，高级工程师"。
3. RAG 检索（**可见性过滤**）：Milvus 按部门标签过滤 → 命中《班车预约规则》公开文档。
4. **Agent 决策**（模型路由层 V4 Pro）：意图=抢总裁班车 → 生成工具调用意向。
5. **权限确定性校验**：Python 携 (userId, resourceType=总裁班车) 调 **Java 权限接口** → Java 查规则表判定。
6. 判定通过 → Python 调 Java `/api/seckill`（传 userId、productId、request_id）。
7. 高并发抢票：令牌桶限流 → 分布式锁幂等 → Redis+Lua 扣库存 → Stream 异步落库。
8. SSE 流式返回：逐步推送 → "抢票成功，座位号 A12"（消息体携带 model 字段）。

### 7.3 反例场景

| 场景 | 拦截点 | 结果 |
|---|---|---|
| Token 过期 | Python 中间件 | 401，不进入 RAG、不调用 Java |
| 职级不足（实习生抢总裁班车） | **Java 权限接口（确定性规则表）** | 返回明确拒绝码 → Python 向用户解释，不扣库存 |
| 部门不可见文档被检索 | Milvus 标量过滤 | 召回结果中不出现，模型无机会引用 |
| 超出令牌桶限流阈值 | Java 限流模块 | "系统繁忙，请稍后重试" |
| 重复请求（相同 request_id） | Java 分布式锁 + 唯一索引 | 返回第一次结果，不重复扣库存 |

## 8. 关键技术决策与利弊总结

| 决策点 | 决策内容 | 理由与利弊 |
|---|---|---|
| 异构双后端 | Java 扛交易，Python 扛 AI | ✅ 各取所长；❌ 跨语言调用开销 |
| **模型两阶段路由** | 开发期 V4 Pro；上线后 Agent/多模态→V4 Flash，全配置化 | ✅ 降本 + 契约与模型解耦；❌ 需维护两档配置与可观测字段 |
| **执行通道收敛** | Agent→Java 只走 REST；MCP 仅作工具注册 | ✅ 避免双契约漂移；❌ MCP 实时调用能力留到外部 Agent 场景再启 |
| **权限硬化** | Java 规则表确定性放行；Milvus 标量过滤可见性；LLM 只解释 | ✅ 安全边界不依赖模型幻觉；❌ 规则表需人工维护 |
| Token 校验前置 | Python 校验失败即拒绝 | ✅ 保护核心交易链路；❌ 增加 Python 层负担 |
| Qwen3-Embedding-0.5B | 仅本地向量化，随进程启停 | ✅ 显存宽裕；❌ 不具备生成能力（已明确分工） |
| Small-to-Big | 存子块向量、返父块全文 | ✅ 精度 + 上下文完整；❌ 存储略增 |
| 令牌桶限流 | Redis+Lua 全局限流 | ✅ 防并发冲击；❌ 增加 Redis 调用 |
| 幂等设计 | request_id 锁 + 唯一索引 | ✅ 防超卖防重试；❌ 锁开销 |
| SSE 流式 | 逐步推送 + model 字段 | ✅ 体验极佳、可观测；❌ 需处理断连清理 |
| Redis Stream | 替代 RabbitMQ，MAXLEN=10000 | ✅ 省资源；❌ 演示级可靠性，可能丢消息 |
| 配置管理 | 环境变量/分档配置文件 | ✅ 部署简单、模型可切；❌ 变更需重启 |

## 9. 资源评估 v2（WSL2 内存账重算）

### 9.1 实际部署拓扑

Windows 16GB 宿主机 + WSL2 Ubuntu。**全部服务（Redis/MySQL/Java/Python/Milvus/vLLM）统一放 WSL2 内存池内**，避免 Windows/WSL2 各跑一半导致内存分裂。

### 9.2 WSL2 内存配置（必须）

在 `C:\Users\<user>\.wslconfig` 设置（示例）：

```ini
[wsl2]
memory=12GB
processors=4
swap=4GB
```

- WSL2 默认最多取宿主机 50%（约 8GB），**不够**。上限给 12GB，给 Windows 桌面留 ~4GB。
- vLLM 在 WSL2 内需 GPU passthrough：Windows 侧装 NVIDIA 驱动（WDDM 3.x，支持 CUDA in WSL），WSL2 内无需重复装显卡驱动，但需注意 vLLM 用 CUDA 依赖。

### 9.3 分池预算（v2）

| 组件 | 预估内存 | 预估显存 | 位置 |
|---|---|---|---|
| Windows 桌面/系统 | ~4GB | 系统占用少量 | Windows |
| Java 服务（含 Tomcat，堆 1GB） | ~1.5GB | 0 | WSL2 |
| Python 服务（FastAPI） | ~1GB | 0 | WSL2 |
| vLLM + Qwen3-Embedding-0.5B | ~1.5GB | ~0.6GB | WSL2（显存） |
| Milvus Lite | ~3GB | 0 | WSL2 |
| Redis | ~0.5GB | 0 | WSL2（Docker） |
| MySQL | ~0.3GB | 0 | WSL2（Docker） |
| WSL2 Ubuntu 系统余量 | ~0.2GB 缓冲 | — | WSL2 |
| **WSL2 合计** | **约 8GB / 12GB 配额** | **~0.6GB / 6GB** | — |

> 显存按 INT8 量化 ~0.6GB 计，6GB 卡留有大量余量给后续本地小模型实验；模型路由层走外网 API 不占本机显存。

### 9.4 启动顺序建议

1. WSL2 Ubuntu（确认 `.wslconfig` 生效：`wsl --shutdown` 后重启）。
2. Redis + MySQL：`docker-compose up -d`（WSL2 内）。
3. Java 服务：`mvn spring-boot:run`（加载权限规则表）。
4. Python 服务：`uvicorn main:app`（加载 embedding + 模型路由配置，dev 档）。
5. 前端：`npm run dev`。
